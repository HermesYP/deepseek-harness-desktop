## 5. Credential handling (port-critical)

**Where API keys are stored today.** The seam keeps secrets out of configuration: settings and `cordis.yml` carry only *references* (POSIX env-var names, `CredentialRef`), providers own values, and consumers re-resolve once per operation (`docs/subsystems/credentials.md:5`, `docs/subsystems/credentials.md:11-15`). The shipped provider `dsh-credentials-local` stores everything in **one plaintext-ish YAML file, `$DSH_HOME/.credentials.yaml`** (config default `path: <harness home>/.credentials.yaml`, `packages/credentials/credentials-local/README.md:42-47`), a versioned document with `refs:` (key values by env-var name) and `records:` (per-plugin `<owner>/<id>` entries tagged `api-key` or `grant`, grant payloads verbatim) (`packages/credentials/credentials-local/README.md:84-109`). Resolution precedence: launch environment (read-only) → stored file → project `.env` → `$DSH_HOME/.env` (`packages/credentials/credentials-local/README.md:71-80`). API keys reach LLM adapters by per-request reference resolution — "the LLM adapters resolve once per model request, so a rotated credential reaches the very next request" (`docs/subsystems/credentials.md:5`); `llm-deepseek` inlines no key: "both resolve per request from the `llm-deepseek:` settings section … with the key coming from the credential store" (`packages/bundle/base/cordis.patch.yml:520-526`), and `deepseek-official` search reuses `DEEPSEEK_API_KEY` per search (`packages/bundle/base/cordis.patch.yml:463-465`). `ctx.deepseekAccount.resolveToken(url)` supplies account tokens only to the inference origin the provider allows (`docs/subsystems/credentials.md:340-344`).

**Is any OS credential store used? No.** No `safeStorage`, `keytar`, `wincred`, `keychain`, `libsecret`, `DPAPI`, or `CryptProtectData` usage exists anywhere in the checkout (searched `_upstream` for each term; zero code hits). The provider is explicit: "Only your OS user can read the file: the product creates it with owner-only permissions… **A same-UID process can read the document** — the file-effect sandbox modes do not deny reads, and **an OS-keychain provider is deferred**" (`packages/credentials/credentials-local/README.md:115`, `packages/credentials/credentials-local/README.md:200`), and the Dev Note names the deferred answer: "An OS-keychain provider — a store the model's processes cannot read … belongs beside this provider as a sibling package" (`packages/credentials/credentials-local/README.md:212`). POSIX loads refuse a group/world-readable file (chmod 600 guidance); Windows skips the mode check (`packages/credentials/credentials-local/README.md:115`). Writes are atomic via `dsh-atomic-write` under a cross-process writer lock with comment-preserving patch semantics and file watching (`packages/credentials/credentials-local/README.md:138-156`, `packages/credentials/credentials-local/README.md:202`). Secrets never round-trip to any UI: `CredentialInfo` has no value slot and "no method here returns one" (`docs/subsystems/credentials.md:36-40`, `docs/subsystems/credentials.md:231`), and diagnostics never quote values (`packages/credentials/credentials-local/README.md:162-164`).

**Provider/service surface.** `ctx.credentials` is an abstract seam (`resolve`/`describe`/`set`/`unset` + `readRecord`/`describeRecord`/`listRecords`/`modifyRecord`/`deleteRecord`) (`docs/subsystems/credentials.md:135-225`); `packages/credentials/` contains `credentials` (seam), `credentials-local` (file provider), `authorization` (flow registry, `ctx.authorization`), `deepseek-account` (abstract account seam) and `deepseek-account-platform` (Platform implementation with an API-only header configuration) (`docs/subsystems/credentials.md:487`, `packages/credentials/*/README.md` listing). The `modifyRecord` read-modify-write is the only record write path, held exclusive across processes for safe token refresh (`docs/subsystems/credentials.md:205-216`). Browser-session cookies for the Web/Desktop Host are backed by the same store: the `client-connection/browser-session` grant record holds the cookie signing secret, loaded into memory at Connection activation (`packages/client/connection/README.md:41`). Embedded Platform account credentials travel only over private Node IPC to main-process Platform views, "account RPC and the Harness renderer receive no token" (`apps/desktop/README.md:13`).

**Port consequence:** moving credentials to OS-backed storage means replacing `dsh-credentials-local` with a sibling `CredentialProvider` implementation (DPAPI/Credential Manager on Windows, Keychain on macOS, Secret Service on Linux) while preserving: the two key spaces (`CredentialRef` layering incl. env precedence, `CredentialKey` records), the `modifyRecord` exclusivity, the empty-value-is-absent rule (`docs/subsystems/credentials.md:139`), and the no-value-on-the-wire property (`docs/subsystems/credentials.md:231`).
