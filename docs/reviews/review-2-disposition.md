# Independent review #2 — findings and disposition

A second read-only review inspected the port and raised five findings. This records what was done about each, with the evidence and the honest residual gaps. Statuses use this repository's vocabulary: `verified`, `implemented`, `specified`, `blocked`.

Scope of the review: it inspected source and staged files and ran one in-memory keyboard probe. It did not modify, rebuild, or launch the application. So every finding is a **source-level** claim; the dispositions below say explicitly where a fix has been exercised and where it has only been implemented.

## Disposition

| # | Sev | Finding | Status | Owner | Evidence |
|---|---|---|---|---|---|
| 1 | P1 | The packaged runtime lacks required dependencies; staging deploys only `dsh-desktop-host`, so the payload has no root `cordis-plugin-group`, `dsh-base` or `dsh-web-app`, and the app's own prerequisite check rejects the layout | **Resolved and verified** | lead + payload lane (`port/scripts/build.ps1`) | **Closure solved, materialization blocked.** `@deepseek-ai/dsh-base` and `dsh-web-app` are *siblings* — neither depends on the other — but **`apps/cli` (`@deepseek-ai/dsh`) depends on both**, so `apps/cli`'s closure plus `desktop-host` is the correct assembly. `cordis-plugin-group` is a **peer** dependency (vendored at `vendor/group`), which `--prod` deploy omits because pnpm satisfies peers only by hoisting to a workspace root a packaged tree does not have; it is now materialized from an explicit list. **But the payload still cannot be produced** — see finding F-17: `robocopy /E` recurses through pnpm's cyclic junctions (measured: 91,429 → 119,227 files in 20 s while `@deepseek-ai` never appeared), and `--config.node-linker=hoisted` fails with `ERR_NPM_UNUSED_PATCH`. The script now **refuses fast with the explanation** instead of recursing |
| 2 | P1 | A host failure before connecting leaves startup waiting indefinitely; `start()` awaits `server.accept()` before taking child ownership or starting the exit monitor, and the control timeout only begins after a connection | **Verified** | `dsh-runtime` lane | Root cause confirmed at `supervisor.rs:263`. Now: ownership is taken **immediately** after spawn, then a `select!` races authenticated accept against the monitor's status and a 30 s connect deadline. Typed errors distinguish `host_startup_child_exit` (**with exit code and stderr tail**), `host_startup_timeout`, connection failure and cancellation; failure cleanup kills the containment tree and waits for the monitor to reap. A related `stop()` edge case (child handle already moved to the monitor while containment still existed) was found and fixed. `cargo test -p dsh-runtime`: **9 unit + 10 integration pass**; `cargo clippy -p dsh-runtime --all-targets -- -D warnings` exit 0. **Residual:** the 30 s timeout branch and the connection-failure branch are implemented but not separately exercised; only the child-exit and immediate-stop paths are |
| 3 | P2 | Onboarding checks a different credential source from the agent runtime: `hasApiKey()` reads the Rust keyring with coordinates that have no initialization path, so a fresh install reports `false`; and it cannot see credentials configured through provider settings or the environment | **Implemented** | `port/ui` lane, with contract amendment A12 | `hasApiKey()` no longer waits for `runtimeBootReady`/`AppInfo` and no longer calls the Rust `credential_has`. It issues **authenticated unary HTTP RPC to existing Host routes** — `settings/describe`, `llm/listConfigurableProviders`, `credentials/describe` (credential **metadata only**, batched at 64) — verified against upstream `apps/desktop/src/welcome-backend.ts` and `packages/api/settings-controller/src/credentials.ts`. **No new host route was required.** A12 records the rule: the **host is authoritative for model credentials**; `credential_*` stays declared but must never gate onboarding; `AppInfo.credentialRef` remains only for the write path. Onboarding test asserts `true` from configured environment-source metadata and checks the route sequence. **Residual: not exercised against a live Host** — the transport is validated with a fetch mock, not a running desktop |
| 4 | P2 | Two-key shortcuts can be saved but cannot execute: the producer emitted one input per `keydown` with no held-key tracking and never emitted `secondCode`, so a saved `Ctrl+A+B` binding never matched | **Verified** | `port/ui` lane | The producer now tracks non-modifier held codes, emits an optional `secondCode` on the second press, tracks `keyup`, and clears on blur, configuration change and recording; delivery is skipped during recording, and composed state is shared with `shortcuts.recording` and the Rust recording event. **Verified to the bar the review demanded** — the test imports the **actual upstream `ShortcutRegistry`**, registers a real command, supplies an accepted `Ctrl+KeyA+KeyB` configuration, drives real `KeyboardEvent`s through the producer and registry, and asserts **`invoked === 1`**; release, blur and recording are covered too |
| 5 | P2 | "Close Page or Window" carries an invalid shortcut revision: Rust initialized `shortcut_revision` to empty, `shell_shortcuts_get` returned a generated revision without updating it, and the menu emitted the stale value, which upstream deliberately discards | **Verified** | `app` lane | The duplicate field was **removed**, not synchronised: menu dispatch and `shell_close_window` now read the revision from the authoritative snapshot. The menu payload keeps upstream's `kind:'menu'` shape with `page.close`. `shell_shortcuts_get` stays side-effect free (only an accepted edit emits `dsh://shortcuts/changed`). Tests compare the dispatched payload's revision against the real `ShortcutPersistence::read_current()` snapshot, before **and** after an accepted edit. `cargo test -p dsh-desktop`: **2 pass**; clippy and `cargo fmt -p dsh-desktop -- --check` clean. **Residual:** the Tauri event loop is not driven, so live delivery is untested |

## What is still unexplained, and must not be papered over

- **`client-modules: HTML did not preload @deepseek-ai/dsh-client-modules/client.js`** — still **unexplained**. The lead's theory that the gateway's local rejection body was HTML is **refuted by measurement** (the rejection is `503`, `text/plain`, body `dsh desktop: host is not ready`). Nobody has measured this since.
- **The payload materialization** (F-17) is the binding constraint on every end-to-end step. Until it is solved, "cold startup" cannot be attempted at all, and no amount of per-component verification substitutes for it.
- Every claim above is a **source or test-level** result. No step in this document was produced by running the assembled application with no development overrides, which remains the only test that establishes the product works.
